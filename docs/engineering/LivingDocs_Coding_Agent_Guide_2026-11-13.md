# LivingDocs coding agent guide — 2026-11-13

Read the current Owner task, repository state, approved contract, migrations, [Master Decisions](LivingDocs_Master_Decisions_Technical_Rules_Team_Agent_Handoff_2026-11-13.md) and [Backend Engineering Standards v3](LivingDocs_Backend_Engineering_Standards_v3.md) before changing code. The Owner's latest explicit decision takes precedence over older draft examples.

Follow LD-D18: read-only audit → exact file allowlist and expected diff → explicit Owner approval → implementation on approved paths → verification → stop for review. A testable vertical slice can require more than three files; do not exceed its approved allowlist. Preserve pre-existing edits and distinguish worktree from index.

For every S01–S04 business service, including one implementation, define a Service interface and implementation in `service/impl`; inject the interface into the Controller. Use constructor injection and set `@Transactional` by use case. Validate request DTOs with Jakarta annotations and `@Valid`; use service method validation only for real method constraints. Map typed business exceptions centrally to RFC 9457 Problem. Follow [Standards v3](LivingDocs_Backend_Engineering_Standards_v3.md#mapping) for MapStruct and sensitive-data boundaries.

Ordinary JSON success bodies use `SuccessResponse<T>` with exactly `code`, `message`, `data`; service-owned `model.SuccessCode` provides `wireCode` and `defaultMessage` through `SuccessResponse.of(SuccessCode, data)`. Never use `enum.name()` as the wire code or store HTTP status in the enum. `ResponseEntity` sets HTTP status/headers. HTTP 204 has no body; redirects, files/streams, webhooks and other protocol-specific responses follow their own contracts. Errors remain RFC 9457 Problem.

For LIV-136 API-001, maintain Register's local-only boundary. Its success response is HTTP 201 with `code: "IDENTITY_REGISTERED"`, `message: "Registration completed"` and `data.identityId` UUID. Keep Flyway V1/V2 intact. Prove the endpoint with real PostgreSQL, migrations, Hibernate validation, runtime request/response assertions, negative cases and comparison of static OpenAPI YAML, runtime Springdoc and Controller DTO. Swagger visibility alone does not make an operation IMPLEMENTED; do not claim other candidate API routes are implemented or bulk-refactor S02–S05. Retain the current Docker Swagger setup.

The current worktree `AGENTS.md` reflects these rules but is Git-ignored and may be absent from other checkouts; Owner must decide how to distribute it. Older drafts in `docs/ai-agent/` may still contain superseded instructions on unwrapped success, Service interfaces or a fixed 1–3-file limit. Treat those passages as historical, not active team rules; do not silently replace or track them outside an approved allowlist.
